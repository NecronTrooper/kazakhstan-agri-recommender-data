## Структура проекта

```
data_collection/
├── 01_faostat.py          # FAOSTAT — производство (урожайность, площади), национальный уровень

├── 07_validate_regions_vs_national.py  # Кросс-валидация 05 против 01
├── 08_grainunion_prices.py  # grainunion.kz — внутренний рынок КЗ (тенге), сбор "на будущее"
├── 09_price_spread.py     # Спред внутренний/экспорт/мировой рынок
├── 10_district_price_snapshot.py  # ИЛЛЮСТРАТИВНЫЙ демо-снимок район×цена (см. ниже — не для методологии)
├── input/                 # Папка для (опциональной) ручной выгрузки stat.gov.kz
└── output/                # Выходные файлы всех скриптов
```


## Внутренний рынок Казахстана (Скрипт 08)

**apk-inform.com** в бесплатном виджете `/ru/prices` даёт по Казахстану
только 2 экспортные позиции в USD (пшеница 3кл DAP ст.Сарыагаш, ячмень
FOB порт Актау) — внутреннего тенгового рынка там нет (видимо, за
подпиской). Их AJAX-эндпоинт `/ru/prices/get-prices` публичный (без
логина, разрешён robots.txt) и рабочий для месячных серий, но не
удалось заставить его отдать именно эти 2 недельные KZ-позиции несмотря
на много попыток — если понадобится, стоит посмотреть DevTools реального
браузера, что именно шлёт фронтенд. Проверил Wayback Machine
(web.archive.org) как альтернативу — не подходит: цены на этой странице
рендерятся тем же AJAX-запросом уже после загрузки, а архивный краулер
JS не выполняет, так что в снепшотах, скорее всего, только пустая форма
без данных (второй запрос за недавними снепшотами 2024-2026 не ответил
за отведённое время — на этом остановился, по согласованию не более
1-2 попыток на источник). Открытый вопрос: можно написать в apk-inform
напрямую с academic-запросом на доступ, если это станет приоритетом.

**gsc.kz** (старый адрес Зернового союза Казахстана) не работает — 404
на всех путях, домен, похоже, заброшен.

**grainunion.kz** — актуальный сайт Зернового союза, раздел
`/ru/news/32` содержит статьи "Еженедельный обзор ценовой ситуации на
зерновом рынке Казахстана" с реальными внутренними ценами EXW-элеватор
(Акмолинская, Костанайская, Северо-Казахстанская области — те же три
целевые области, что и в 05_kaz_stat.py) в тыс.тенге/т, плюс экспортные
цены в USD. Формат — консистентные буллеты
(`▪️Пшеница 3 кл (кл-на 23-24%) - 88 - 92 ▶️ (0)`), парсится regex'ом,
не NLP.

**Важно:** этот структурированный формат обзоров стартовал только
25.05.2026 (проверено постранично по всему архиву новостей, который в
остальном уходит в 2019 год, но состоит из разрозненных пресс-релизов —
не еженедельных ценовых обзоров). На 2026-09-09 доступно 12 выпусков
(~3.5 месяца). Это НЕ ретроспективный сбор истории — `08_grainunion_
prices.py` спроектирован для периодического перезапуска (например, раз
в неделю через cron/Task Scheduler): каждый запуск дозаписывает только
новые выпуски, история будет накапливаться со временем. Данные —
`output/08_grainunion_domestic_prices.csv`, курсы валют Нацбанка РК за
ту же неделю (нужны для перевода тенге в USD без внешнего FX-источника)
— `output/08_grainunion_fx_rates.csv`.

## Спред внутренний/мировой рынок (Скрипт 09)

`09_price_spread.py` считает по каждой неделе (пшеница 3 класс,
усреднено по подклассам):

  - **export_spread** — цена экспорта DAP ст.Сарыагаш минус внутренняя
    цена EXW-элеватор, обе в USD/т за одну и ту же неделю (курс
    Нацбанка РК берётся из того же выпуска обзора). Прямое, "яблоки к
    яблокам" сравнение внутри Казахстана.
  - **world_spread** — внутренняя цена (переведена в USD) минус мировая
    цена (World Bank Pink Sheet, wheat_hrw). Из-за лага публикации Pink
    Sheet (на 2026-09-09 последний доступный месяц — декабрь 2025)
    используется последняя известная мировая цена через as-of merge, а
    не тихий NaN — с явной пометкой в колонке
    `world_price_months_stale`, на сколько месяцев она отстаёт от даты
    обзора.

Результат на 2026-09-09: экспорт в среднем на **+21%** дороже внутреннего
рынка, внутренняя цена — на **-8.4%** ниже (устаревшего на ≤8 мес.)
мирового бенчмарка. Данные — `output/09_price_spread.csv`.

### Методологическое примечание про глубину истории

12 недель (с 25.05.2026) — это меньше одного полного сезонного цикла,
поэтому спред-ряд **не самостоятельная модель** (ARIMA/Prophet и т.п.
на нём одном не строится — нужно 1-2+ полных цикла). Рекомендуемый
подход для диссертации:

  1. Основную модель цены обучать на длинной истории (World Bank Pink
     Sheet, 1990–2025 + FAOSTAT producer price).
  2. Внутренний спред (09) использовать как **дополняющий/корректирующий
     признак** поверх этой модели на последних неделях — честный
     компромисс между "модель нужна" и "истории мало", а не попытка
     обучить отдельный ряд на 12 точках.
  3. В разделе "Materials and methods" явно писать: *"Недельные
     внутренние цены собираются с 25.05.2026 автоматизированным
     скриптом, настроенным на непрерывное накопление истории; на момент
     подготовки работы доступно N недель, что ограничивает независимое
     обучение временного ряда на этих данных — они используются как
     дополняющий признак, а не как самостоятельный источник прогноза"* —
     формулировка, прозрачная для рецензента, вместо риска, что дата
     охвата всплывёт как вопрос на защите.

## Данные stat.gov.kz (Скрипт 05) — реальные региональные ряды

У stat.gov.kz нет публичного REST API для растениеводства, но у каждой
области есть страница **"Динамические ряды"**
(`stat.gov.kz/ru/region/<slug>/dynamic-tables/1485/`) с прямыми ссылками
на xlsx-файлы с историческими рядами 1990/1991–2025. `05_kaz_stat.py`
скачивает и парсит их напрямую (с кэшем в `output/stat_gov_kz_cache/`) —
никакого ручного экспорта не требуется.

**Детализация отличается между областями** (это свойство источника, а
не пробел скрипта):
- **Костанайская и Северо-Казахстанская области** публикуют данные по
  **отдельным культурам** (Пшеница, Ячмень, Кукуруза, Подсолнечник) в
  разрезе районов — отдельными файлами.
- **Акмолинская область** публикует растениеводство на уровне **крупных
  групп** ("Зерновые и бобовые", "Масличные") напрямую, но у части
  культур внутри группы данные тоже есть — просто не отдельным файлом, а
  встроенным подблоком "из них: пшеницы" / "из них: семена
  подсолнечника" внутри файла группы, с ПОВТОРНОЙ районной разбивкой уже
  для этой культуры (обнаружено и распаковано 2026-09-09). `05_kaz_stat.py`
  теперь извлекает и группу, и вложенную культуру как отдельные записи:
  группа помечена `source = stat_gov_kz_real_group`, распознанная
  культура (Пшеница/Подсолнечник) — `source = stat_gov_kz_real`, то есть
  той же меткой, что у Костаная/СКО, и сливается с их данными по той же
  культуре в `05_kaz_stat.csv`. Ячмень/кукуруза Акмолинской области
  такого подблока не имеют — там доступна только группа целиком; площадь
  подсолнечника (в отличие от сбора/урожайности) тоже не разбита отдельно
  — это уже реальное ограничение источника, а не пропуск парсера.
- **Рапс** ни одна из трёх областей не публикует регионально — по рапсу
  в проекте есть только национальные данные FAOSTAT (скрипт 01).

Эффект на кросс-валидацию (07): после добавления Акмолинской пшеницы
доля трёх областей от нацио­нального производства пшеницы (FAOSTAT)
выросла с ~51% (только Костанай+СКО) до **77%** (медиана) — сильный
дополнительный сигнал достоверности, соответствующий общеизвестному
факту, что Акмолинская, Костанайская и Северо-Казахстанская область —
это "северный зерновой треугольник", дающий основную часть пшеницы
Казахстана.

Единицы измерения тоже отличаются по файлам (например, у Костаная площадь
и сбор — в тысячах га/тонн, у СКО и Акмолинской — в штучных
гектарах/центнерах); скрипт определяет единицу динамически по подписи в
самом файле, а не считает её постоянной.

### Районный уровень (05_kaz_stat_districts.csv)

`05_kaz_stat.py` дополнительно строит районную разбивку (не только итог
по области), сохраняя её ОТДЕЛЬНО от `05_kaz_stat.csv` — в
`output/05_kaz_stat_districts.csv`. Она НЕ подмешивается в
`06_merge.py`/`master_dataset.csv`: климат (ERA5) и почва (SoilGrids) в
основном пайплайне остаются на уровне области (см. решение и обоснование
выше — точечная выборка климата "по одному пикселю на район" была бы
методологически слабее нынешнего областного среднего; правильная
зональная статистика по полигонам районов — отдельная задача).

Формат: `year, region, district, crop, area_ha, yield_kgha,
production_ton, source`. Строка `district = "Область (итого)"` дублирует
`05_kaz_stat.csv` для удобства сравнения. Как и в оболастном файле, у
Акмолинской области здесь есть районные ряды не только по группам
культур, но и по вложенным подблокам "из них: пшеницы"/"из них: семена
подсолнечника" — распакованы наравне с группами (`crop = "Пшеница"` /
`"Подсолнечник"`, `source = stat_gov_kz_real`), поэтому Акмолинская
пшеница/подсолнечник теперь доступны и на районном уровне тоже, а не
только областная сумма.

**Валидация**: скрипт при каждом запуске сверяет сумму `production_ton`
по районам с строкой "Область (итого)" для каждого (регион, культура,
год) — на 2026-09-09 из 375 проверенных групп совпадает 371 (98.9%), 4
расхождения — кукуруза в Костанайской области (второстепенная культура
с абсолютными объёмами в сотни-тысячи тонн на всю область, где пара
тонн погрешности даёт заметный процент; не признак ошибки парсинга; эти
4 строки видны напрямую в выводе скрипта при запуске, если понадобится
перепроверить).

### Ручная выгрузка (опционально)

Если нужны данные за пределами трёх целевых областей, их всё ещё можно
выгрузить вручную и они получат приоритет над автозагрузкой:
1. Перейти на https://stat.gov.kz
2. Статистика → Сельское хозяйство → Растениеводство → экспорт Excel
3. Сохранить в `input/stat_gov_kz_crops.xlsx`
4. Запустить `python 05_kaz_stat.py`

### Если сайт недоступен

Скрипт откатывается на синтетические данные (см. `generate_synthetic_kaz`
в 05_kaz_stat.py) — они явно помечены в колонке `source` суффиксом

строки попадают в master_dataset.

## Методологическая позиция: районные данные (05) vs цена (08/09)

Изначально рассматривался прямой join `05_kaz_stat_districts.csv`
(урожайность по районам, 1990–2025) с `09_price_spread.csv` (цена/спред,
понедельно с 25.05.2026) по ключу (область, год, культура). Проверка
2026-09-10 показала, что эта схема не соответствует структуре
источников:

  1. **У цены нет региональной оси.** grainunion.kz публикует ОДНУ цену
     EXW-элеватор сразу на "Акмолинскую, Костанайскую, Северо-
     Казахстанскую области" одной сводкой — это не пробел в данных, а
     структурное свойство рынка: элеваторные цены Зернового союза
     формируются и публикуются как единая сводка по региону сбыта, а не
     раздельно по области.
  2. **Нет общего года.** Районные данные — 1990–2025 (годовые),
     ценовые — только недели 2026 года. Join по `year` при текущей
     глубине истории даёт пустой результат.

**Решение: два независимых слоя, не смешиваются в один join.**
  - `05_kaz_stat_districts.csv` (+ `05_kaz_stat.csv`) — питает модель
    прогноза урожайности, как и раньше.
  - `08_grainunion_domestic_prices.csv` / `09_price_spread.csv` —
    отдельная задача (прогноз цены / рекомендация "продавать сейчас или
    ждать"), растёт понедельно с 25.05.2026.

**Конкретный триггер для join** (а не абстрактное "когда-нибудь"): когда
у 08/09 накопится история, покрывающая хотя бы один полный
сельскохозяйственный цикл — с уборки урожая в сентябре 2026 по конец
сезона реализации в августе 2027 — появится содержательная связь
"урожай текущего года × цена текущего сезона его реализации". На этот
момент ключ join — **(year, crop)**, БЕЗ региональной оси (см. пункт 1
выше — добавлять область в ключ бессмысленно, у источника цены её
структурно нет).

**10_district_price_snapshot.py — демо, не методология.** Есть готовый
скрипт, который прямо сейчас соединяет последний доступный год районных
данных (2025, факт) с последней доступной неделей цены (конец
августа/начало сентября 2026) — это осознанный date-mismatch
("сегодняшняя цена на урожай прошлого сезона"), полезный только чтобы
показать, что recommender-слой технически принимает оба входа
(например, для демонстрации научруку). **Использовать
`output/10_district_price_snapshot.csv` как исторический факт о 2025
годе или как валидированный источник для модели — методологически
некорректно**; в тексте работы этот файл не должен фигурировать как
компонент методологии, только (при необходимости) как иллюстрация
механики recommender-слоя.

## Настройка ERA5 (Скрипт 03)

1. Зарегистрируйтесь на https://cds.climate.copernicus.eu
2. Получите Personal Access Token в профиле
3. Создайте файл `~/.cdsapirc`:

## Кросс-валидация (Скрипт 07)

`07_validate_regions_vs_national.py` независимо проверяет региональные
данные (05, stat.gov.kz) против нацио­нальных (01, FAOSTAT) — сумма
area_ha/production_ton по Акмолинской+Костанайской+СКО не должна
превышать нацио­нальный итог, и её доля должна быть стабильна год к
году. Результат на 2026-09-10 (после исправления бага с кодом страны и
распаковки встроенной районной разбивки Акмолинской по пшенице/
подсолнечнику, см. ниже):

| Культура | Доля от нац. производства (мин–медиана–макс) | Стабильность (CV) |
|---|---|---|
| Пшеница (Акмолинская+Костанай+СКО) | 57–77–88% | 0.09 (стабильно) |
| Ячмень (Костанай+СКО) | 26–41–54% | 0.16 (стабильно) |
| Зерновые и бобовые, группа (Акмолинская) | 17–25–28% | 0.12 (стабильно) |
| Подсолнечник (Акмолинская+Костанай+СКО) | 1–9–29% | 0.74 — выше, но культура второстепенная (малая абсолютная база), не признак ошибки |
| Кукуруза, Масличные (группа) | единицы % | высокий CV — ожидаемо, культуры второстепенные для этих областей, малая абсолютная база |

Ни одного года с долей >100% ни по одной культуре. Доля пшеницы выросла
с ~51% (только Костанай+СКО, до распаковки Акмолинской) до **77%**
(медиана, все три области) — хорошо согласуется с общеизвестным фактом,
что Акмолинская, Костанайская и Северо-Казахстанская области — это
"северный зерновой треугольник", дающий основную часть пшеницы

## Известные ограничения и найденные проблемы (2026-09-09 — 2026-09-10)

- **[ИСПРАВЛЕНО, но важно для методологии] Код страны в 01_faostat.py был
  неверным.** `KAZ_AREA_CODE = 63` в исходной версии скрипта на самом
  деле соответствует **Эстонии**, а не Казахстану (проверено прямым
  чтением `Area`/`Area Code` из bulk-файла FAOSTAT). В результате
  `01_faostat.csv` молча содержал сельхозданные Эстонии под меткой
  "Kazakhstan" — код `result["country"] = "Kazakhstan"` был жёстко
  прописан и ничего не проверял. Обнаружено скриптом 07 (доля регионов
  от "нацио­нального" итога доходила до 8900%, что физически
  невозможно). Исправлено на правильный код **108**, добавлена
  автоматическая проверка (`filter_kazakhstan` в 01_faostat.py теперь
  падает с понятной ошибкой, если реальное название страны в данных не
  содержит "Kazakhstan"). **Если где-то в диссертации/статье уже
  использовались значения из старой версии 01_faostat.csv (урожайность
  ~130 тыс. га пшеницы вместо ~12 млн га) — их нужно пересчитать.**
- **Оперативные данные МСХ РК за 2024 год удалены из пайплайна** (ранее —
  `05_moa_harvest_2024.csv`). Цифры были жёстко зашиты в код без
  проверяемой ссылки на первоисточник — не найдено подтверждающего
  пресс-релиза, поэтому файл убран целиком, а не оставлен с пометкой
  "непроверено". Если понадобятся оперативные итоги 2024–2025, добавлять
  только с точной ссылкой на публикацию МСХ РК/stat.gov.kz.
- **[ИСПРАВЛЕНО] ERA5: осадки/испарение/радиация были занижены в ~N раз
  (N = число дней в месяце).** Для `product_type=monthly_averaged_
  reanalysis` Copernicus CDS отдаёт накопительные переменные
  (`total_precipitation`, `potential_evaporation`,
  `surface_solar_radiation_downwards`) как СРЕДНЕСУТОЧНУЮ скорость за
  месяц, а не как сумму за месяц — задокументированная, но не самая
  очевидная особенность ERA5/ERA5-Land (см. confluence.ecmwf.int,
  pageId=197702790: `tp[мм] = tp[м/сутки] × 1000 × N`). Без поправки на
  N дней в месяце годовая сумма осадков по зерновому поясу выходила
  ~13 мм/год вместо реальной нормы ~350–400 мм/год. Исправлено в
  `nc_to_df()` (03_era5_climate.py) — теперь умножается на
  `calendar.monthrange(year, month)[1]`. Пересчитано по уже скачанному
  кэшу `.nc`, повторной загрузки с CDS не потребовалось. После фикса
  засушливые 2021–2022 годы (документированная региональная засуха)
  корректно показывают пониженные осадки — ещё одна независимая
  перекрёстная проверка.
- **[ИСПРАВЛЕНО] SoilGrids: коэффициент пересчёта единиц не применялся
  вообще ни к одному из 8 свойств почвы.** Поле в реальном JSON-ответе
  API называется `d_factor`, а не `conversion_factor`, как было в коде
  (`layer.get("unit_measure", {}).get("conversion_factor", 1)` —
  всегда тихо возвращал дефолт 1). Из-за этого глина+песок+ил
  суммировались в ~1000 вместо ~100% (физически бессмысленно), pH
  показывал 65–80 вместо 6.5–8.0, и т.д. — по всем 8 свойствам.
  Исправлено на `d_factor` в `parse_soilgrids_response()`
  (04_soilgrids.py), данные пересобраны заново со всех 20 точек.
- **Рапс** — нет регионального источника (см. выше), только национальный
  FAOSTAT.
- **[ЧАСТИЧНО ИСПРАВЛЕНО 2026-09-09] Акмолинская область** — изначально
  считалось ограничением методологии, что там доступны только группы
  культур, не отдельные культуры. Оказалось, что файлы группы содержат
  встроенный подблок "из них: <культура>" с реальными данными по
  Пшенице и Подсолнечнику (см. выше) — теперь извлекается и мержится с
  данными Костаная/СКО по этим же культурам. Ячмень и кукуруза
  Акмолинской области такого подблока не имеют — для них по-прежнему
  доступна только группа "Зерновые и бобовые" целиком, это остаётся
  реальным ограничением источника.
